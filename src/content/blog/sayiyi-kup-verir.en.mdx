When a manager asks “why did scrap increase last month?”, a verified answer can take days. But there is a more basic problem: the company often waits for someone to formulate the right question before an important change is investigated at all.

Dima is designed to reverse that loop. The system monitors company data, creates a finding when a meaningful deviation or opportunity appears, and lets the user investigate why it happened and what can be done next.

For that to be trustworthy, one distinction is essential:

**A model can help with the investigation. It should not invent the number.**

## Where the numeric result comes from

A language model can write a useful explanation and translate a complex question into business terms. But the difference between 82.4 and 84.1 is not a matter of producing a plausible sentence.

In Dima, numeric authority should remain in the semantic and analytical layer:

1. The business metric is mapped to a defined measure.
2. The query is planned and bounded before execution.
3. It runs against the real data source.
4. The result travels with its source, period and entity context.

The LLM can explain that result; it should not fabricate it.

## A finding is more than a number

“Scrap increased” is not enough to make a decision.

A useful finding needs to answer questions such as:

- When did the change begin?
- Which products, machines, shifts or orders concentrate it?
- What behavior was considered normal?
- Did the same pattern appear before?
- What is the financial or operational impact?
- Which explanations are supported, and which have been eliminated?

That is why Dima's investigation layer does not leave a KPI on a result screen. It follows the relevant entities and relationships to examine root-cause candidates.

## Where chat enters the flow

Chat does not have to be the starting point.

When a user opens a finding, the context is already known: selected lobe, entities, period, evidence and investigation. If the user asks “what happens if we exclude this customer?” or “how does this option affect delivery?”, the conversation continues the same investigation.

That distinction matters. The user does not need to explain the company to the model again in every prompt.

## Why evidence is part of the product

Even a correct result is difficult to defend in a meeting if nobody can see where it came from.

Evidence therefore should not live only in a technical log. The finding should expose:

- data source,
- period used,
- relevant entities,
- calculation or query result,
- relationships used in the investigation.

Dima's goal is not to say “AI answered”. It is to answer: **why should this finding be taken seriously, and what data supports it?**
